## Gotchas

- **The agenda is the single source.** `buildAgenda` (`server/src/modules/practice/domain/agenda.ts`) feeds three places: the prompt (each seat's items), the per-seat `ask_question.topicId` enum, and scoring (rebuilt at submit and stored on `sessions.agenda`). Change topics there only. The app takes the agenda from the token response and doesn't mirror it. `CAP_MINUTES` in the app's `constants.ts` mirrors `capMinutes` in `identity/domain/plan.ts`. With an older server (no `agenda` in the token) the engine falls back to no agenda rules.

- **No expo-notifications next to RN Firebase messaging.** Both register a FirebaseMessagingService and only one receives messages. The notification icon, colour and channel name come from `plugins/with-notice-notifications.js` plus `firebase.json` instead.
- **Push goes to tokens, not users.** `push_tokens` is keyed by FCM token (one row per phone); sign-in upserts it to the current account and sign-out deletes it. Never put the full notice body in a push: `pushBody` trims it to about 160 characters.
- **Filtered notices are a snapshot.** A notice with `segment` set is visible only through its `notice_recipients` rows (written once, at send time). Don't evaluate the filters at read time. The admin's filter values (`lib/notice-audience.ts`) must match `Segment` in `server/src/modules/notices/domain/notice.ts`.
- **Gestures need the root wrapper.** `app/_layout.tsx` renders a `GestureHandlerRootView` (added for the floating notice); keep it as the outermost view or every `GestureDetector` stops responding.

- **`client/promo` is one timeline, not scenes.** `src/Promo.tsx` choreographs everything against the beat starts `B.*`, and the phone follows the `PATH` keyframes. Retime by changing a line or `MIN` in `script.ts`, not frame numbers. Render with `bun run render`; a full render takes about 3 min.
- **`client/promo` copies art and facts.** `src/art/deemo.ts` and `panel-face.ts` are copies of the site's (a fourth copy of the owl). The panel and report scenes restate the lineup and rubric names. Update them if those change. Edit the lines in `src/script.ts`, then delete that line's `public/audio/vo-<id>.mp3` and run `bun run audio`; scene lengths follow automatically. The ElevenLabs Music API is paid-only, so on a free plan the script falls back to a 30 s looping sound-effects bed.

Editing the field to a non-computing one resets the project's domain to "General" (`editAnalysis`).

Saved sessions store **persona** indices (converted in `fromLive`), so results read `PANEL[who]` directly; older sessions had seat = persona. The ask_question `panelist` value stays the persona id (Chair/Technical/Methodology) even when Santos is "Clinical". The server reads the course at every token mint (ponytail note in `live-token.ts`).

- **Course profile:** the course comes from the account on the server (`courseOf(account.course)` in `live-token.ts` and scoring), never from the app; a null or unknown course reads as "Other". `"General"` is the domain for non-computing courses, and `fieldFocus` ignores an IT field unless the course is BSIT/BSCS. Prompts must stay program-neutral: don't re-add "BSIT" to the panel, analysis or scoring prompts (the study population lives in the paper, not the app). Keep `COURSES` identical in `server/.../identity/domain/course.ts` and the app's `constants.ts`.

- **Sequential panel = one Live session per panelist.** The engine's `seat` picks the token (`seat` in the token request), the voice and the prompt; resumption handles belong to one seat (a handover clears it). Only seat 0 touches the daily cap (`decideStart`); seats 1–2 go through `decideSeat`, which needs seat 0's start to have its token. With one panelist nothing of this runs.

- **Live voice:** chosen only at session start and kept through resumption; a voice inside the ephemeral token is ignored, so the app sends `speechConfig` in its setup message (the token leaves it unlocked). That's why each panelist has their own session (sequential panel).

- **The panel's mouth reads `panelVoice`** (`src/live/voice-level.ts`), written only by the live engines: `GeminiEngine` from an `AnalyserNode` between its voice queue and the speaker (keep it in the graph if the audio path changes), `MockEngine` with fake syllables. Never word a tool refusal as something the model could say aloud or act on ("say it now"); mute instead. Any new path that hands the floor back to the student without `endStudentTurn` must reset it, or the panel's next question is refused.

The `admin` custom claim reaches the token only after the admin signs out and back in. Browsers can call `/admin` only from `ADMIN_ORIGINS` (plus `http://localhost:3001`).

After a server-side change the app makes itself, call `refresh(true)` or `invalidate` the store's freshness, or the change shows up only after a minute or a pull to refresh.

To update three.js, rebuild `vendor/three.js` from an entry that does `export * from 'three'` plus the `RoomEnvironment` addon. - **Avatars:** the face is a DiceBear seed in `users/{uid}.avatar` (absent = the uid-hash default, computed by the server only). The picker shows fixed pages of faces (`pageOfFaces` in `utils/avatar.ts`: FNV-1a of `deal-<page>-<i>`, the same for everyone), so reopening it or going back to a seen page is served from the image cache; only a never-seen page downloads its 8 PNGs (under DiceBear's 10 PNG/s limit; a 429 just shows initials for that tile). Each opening starts at page 0.
- **DiceBear:** the public API is free for non-commercial use (fine for the capstone; self-host or switch to `@dicebear/core` 10.x + `@dicebear/styles` with `SvgXml` for a commercial release). It rejects a color list whose comma is URL-encoded (`%2C`), and its CDN caches by the normalized URL, so one bad request can make the good form fail too; `avatarUrl` builds the query by hand. Each avatar load tells DiceBear the device IP and the hashed seed.
- **Display names:** the server owns the name: `PATCH /me { name }` writes the `users` row, then the Firebase `displayName` (and reverts the row if Firebase refuses). The Firebase-to-row sync only fills an empty name, so a token minted before a rename can't undo it. During sign-up (email not yet verified, the server refuses) the app sets the Firebase name directly and the server copies it on the first verified request.
- **Email verification:** the server rejects unverified email accounts (403), so `use-session.ts` only loads `/me` once `user.emailVerified` is true, and the root layout only refreshes projects for `signedIn && verified`. Firebase reports verification only after `reload(user)`, and the ID token keeps `email_verified: false` until a forced refresh (`checkVerified` does both). Accounts made before this change must verify once.
- **Build and update environments are separate:** preview OTA publishes must use `--environment preview`. A correct EAS Build log and `--clear-cache` do not repair an already downloaded OTA bundle. The installed release can run the newest compatible downloaded update even offline; clearing Android app data deletes that update cache as well as the sign-in state. Repair by publishing a correct compatible update and cold-launching online; preserve app data. Keep the API URL plain text or sensitive in EAS so Update can read it. Release exports now require HTTPS; local development still permits the USB localhost fallback.

- **Session admission:** quota counts issued starts, including abandoned/early-ended rounds. Pending mints lease for 30 seconds; provider fetch times out after 20 seconds and failures refund only their own reservation. Token expiry stays fixed at admission (chosen length + 30 minutes); a very long pause requires a new round.
